# Host and VM log collection

The Linux collector sends audit executions, system journal entries and Docker stdout/stderr to `https://api.hanasand.com/api/logs/ingest`. Original levels are retained; Mill assigns the separate detection severity. Every execve/execveat from every user and service is audited. Shell built-ins do not create execve events; a shell invocation retains its command arguments. Audit collection requires root and kernel audit support.

Run `install.sh <host-id>` as root on Debian/Ubuntu (Python 3.9+, systemd). It installs persistent audit rules, the collector and an enabled service, but does not start delivery. Configure its protected credential, then start it only after the ingestion API is ready:

```sh
python3 configure.py inspur /path/to/protected/log-ingest.json
systemctl start hanasand-log-collector
```

The credential source is a root-restricted JSON object containing `LOG_INGEST_TOKEN`, generated outside source control. `configure.py` preserves existing collection start time, writes mode 0600 and prints no credential. Use the dedicated ingestion credential, never a human session or a broad VM API token. A remote credential may be supplied on standard input with `-`. Do not put it in command arguments, logs or shell history.

State is stored under `/var/lib/hanasand-log-collector` and only advances after acknowledged durable ingestion. Stable event IDs make retries safe. Journal rotation resumes by timestamp; audit rotation uses ausearch's checkpoint recovery. A failed Docker container does not block other containers. Sources run independently, journal reads are limited to 1,000 entries, and historical Docker reads advance one minute at a time. A separate audit cursor starts within the last 60 seconds and prioritizes current host executions whenever the historical audit checkpoint is more than 30 seconds behind, including after an outage; guests send recent executions before each export that is still catching up. All paths share stable event IDs for safe deduplication. `HANASAND_LOG_CONFIG` and `HANASAND_LOG_STATE` support a restricted user service that collects readable journal/Docker logs; this does not grant audit access.

A Docker source that times out may switch to a locally readable `json-file` stream. It retains the original timestamp cutoff and scans history in bounded chunks with inode/byte-offset checkpoints, while an independent live cursor captures new writes. Both advance only after delivery acknowledgement. Canonical IDs include [Docker’s nine-digit timestamp padding](https://docs.docker.com/reference/cli/docker/container/logs/); single-line CLI replay IDs remain unchanged. CLI continuation text is now retained, so corrected full multiline events may overlap formerly truncated legacy records. Plain CLI text cannot always distinguish timestamp-shaped continuation lines or adjacent unterminated records; JSON record boundaries are authoritative.

When Docker removes a container and its source files disappear, collection preserves the acknowledged cursor files and archives the source after delivering one stable high-severity notice that final coverage is unknown. A same-name replacement automatically adopts readable JSON-file collection with its own identity and existing cutoff. CLI collection never scans timestamps before the verified container creation time. Retired unavailable sources remain counted in source health details; their files cannot be reconstructed.

Uncompressed rotated files are completed in order. Active partial JSON lines wait for completion; a closed rotated fragment is preserved as a redacted error event with byte length/hash/offset before advancing. Truncation or unavailable file identity generates an explicit notice before retained contents are replayed. Sources with existing gzip archives remain on the CLI. If compressed history appears after enrollment, the file history cursor stops with an explicit error; the independent live path continues, and no compressed history is silently skipped. Other drivers and sources without local file permissions continue using the CLI. No source files or retention settings are changed.

On LXD hosts, the collector discovers running guests every 30 seconds, installs the same audit rules and reads guest audit, journal and Docker events through LXD. Each guest keeps an export spool and separate cursors until the host acknowledges successful ingestion. The ingest credential never enters a guest. Guest events identify both the physical host and VM. Stopped guests are left stopped and enrolled the next time they run; installation/network failures remain visible in high-severity collector health events. This cannot collect events occurring before a new guest's first audit enrollment. Full VMs need a working LXD agent; unprivileged containers cannot independently enable kernel auditing and report that limitation.

The installer raises small rotating audit stores to 100 MB per file and 20 files when disk space permits, leaving at least another 2 GB free. Existing larger retention and non-rotating security policies are preserved; existing audit files are not deleted. Unavailable historical source files cannot be reconstructed by the collector.

Structured secret fields, common password/token flags, HTTP credentials, cookies and authorization values are redacted before delivery. Redaction is best effort: positional or unusually named secrets may remain in command arguments, so log access must remain restricted. Source output is not modified. The Linux collector does not cover macOS, unreachable hosts or machines lacking administrative access; report those gaps explicitly.

Run regression checks with `python3 -m unittest discover -s ops/log-collector -v`. Verify a real harmless `whoami` execution reaches Mill as `ProcessLogs` on each enrolled host and guest; dangerous patterns belong only in synthetic fixtures.
